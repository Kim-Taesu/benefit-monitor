# 발견·조건 조사 비교 시험 v1 — 실행 전 고정 기준

상태: 설계 확정. 2026-11-05 입력30개 URL·해시 및 대상 HTML 확보 완료, 조건 판독·최종 채점은 별도. 이전 저장 기사 30건은 개발 자료이며 독립 평가 표본으로 재사용하지 않는다. 기존 API 도입의 6분야 최종 평가를 대체하는 시험이 아니라, 합의한 3분야의 선행 발견·조사 시험이다.

## 비교군과 입력

- A: 실행 시점의 수정하지 않은 Python 수집기. commit, sources.yaml, 기준 시각과 공개·후보 snapshot 해시를 고정한다.
- B: 동일 시작 URL·기준 시각·허용 도메인·요청 예산을 받는 Codex 조사. A 출력과 정답지는 제공하지 않는다. 외부 LLM API 호출은 하지 않는다.
- 신규성은 공개본뿐 아니라 기존 후보 목록 전체와 대조한다. 제목 변경·중복 기사·다른 URL의 같은 행사·종료 행사·단순 기사 보충은 신규 혜택으로 세지 않는다. 기관+프로그램+회차+적용기간으로 중복을 검토한다.
- 주관기관 공고가 없고 시민기자 기사만 있는 항목은 `candidate_only`로 남기며 신규 유효 혜택 목표 달성 건수에 포함하지 않는다.
- 단순히 수동 연결이 없는 출처에서 발견한 것은 `coverage_expansion`으로 구분한다. 기존 파서와 같은 자료에서 조건 해석이 개선된 `interpretation_gain`, 링크 추적으로 조건을 해결한 `research_gain`과 섞지 않는다.

## 표본 설계

30개 평가 칸을 준비했다. 문화·운동 10 / 장보기·멤버십 10 / 청년·1인가구 10. [case-register.csv](case-register.csv)는 실제 혜택 목록이 아니라 URL·해시·평가를 채울 등록부다.

각 분야 개발 4건, 보류 6건(총 개발12/보류18)으로 사전에 분리했다. URL과 원문을 잠근 뒤 보류 결과를 보고 프롬프트를 바꾸면 그 표본은 개발로 전환하고 새로운 보류 표본을 확보한다. 30건은 통계적 성능 보장이 아니다.

- 문화·운동: 공공서비스예약, 구 문화·체육시설, 평생학습, 국가유산 공식 목록에서 로테이션.
- 장보기·멤버십: KT·CU·세븐·이마트24·공식 마트 자료. 같은 브랜드는 원칙적으로 3건 이하. 불가능하면 부족을 보고하며 임의 대체로 범주를 채우지 않는다.
- 청년·1인가구: 구청·청년시설, SH, 공유누리. 서울시 기사에서는 주관기관으로 연결해 확인.
- 같은 행사의 홍보 기사와 신청 페이지는 별도 표본이 아니라 같은 표본의 문서 묶음이다.
- 신규 발견 후 조건을 조사하는 시험과 이미 알려진 후보의 누락을 해결하는 시험을 분리 기록한다. 현재 신청 가능성을 확인하지 못하면 ‘유효’로 판정하지 않는다. 실시간 좌석·개인 자격은 보장하지 않는다.

## 비용·요청·중단

- 기본 운영 한도 60, 절대 상한100. 기존 config75를 늘리지 않으며 이 시험은 더 작은 60을 적용한다.
- 한 비교 실행은 최대3쌍. 쌍당 A10/B10 요청 시도, 전체60 이내. robots·첨부·실패·리다이렉트도 포함한다. 같은 실행에서 예산을 reset하여 계속 조사하지 않는다.
- 30쌍을 한 번에 실행하지 않는다. 이후 회차는 별도 실행으로 기록하고 운영 수집기와 동시 실행하지 않는다. 누적 요청 수도 보고한다.
- 대상당 연결 깊이3, 문서5개, 시간5분 상한 중 먼저 도달하면 종료한다. 운영 어댑터는 아직 미구현이므로 실행자가 로그로 강제하고 구현 전 무인 실행 금지.
- 양쪽의 6시간 구 캐시·15분 실패 대기를 존중한다. 재현 추출 시험은 같은 스냅샷, 실시간 탐색 시험은 원문 시각 차이를 기록한다. 로컬 캐시 읽기를 새로운 HTTP 성공으로 세지 않는다.
- DNS·TLS·robots·접근 거부 시 우회하지 않고 blocked로 남긴다. 환경 실패를 모델의 사실 오류로 세지는 않지만, 전체 시도 분모에서 감추지 않는다.

3. 거주/생활권/연령/소득/가구/멤버십 등급 중 어떤 조건과 예외가 있는가?
4. 참가비·재료비·최소 구매액·포인트 차감·제외 품목·취소 비용은 무엇인가?
5. 최대/정액/실비/추첨/선착순 중 어떤 구조인가? 재고·예산 불확실성은 있는가?

8. 인접 혜택을 묶을 근거가 있는가? 중복 적용과 절약액 합산은 공식 확인했는가?

## 채점·달성조건

사람이 공식 자료로 정답과 중요도를 작성하는 것을 최종 기준으로 한다. Codex의 교차 검토는 예비 평가로 표시한다. 인용 문자열 일치만으로 의미 정확도 통과 처리하지 않는다.

| 지표 | 고정 계산 / 기준 |
|---|---|
| 신규 유효 혜택 | A와 기존 snapshot에 없고 주관기관·현재기간·서울 적용·주요 비용 확인된 고유 혜택. 초기 목표 분야별3건, 총9건 |
| 조건 해결 | 실행 전에 등록한 중요 질문20개 중 추가 공식 문서로 답을 확정한 질문10개 이상. 같은 사실 반복·미확인 목록 작성은 해결0건 |
| 중요 오류 | 날짜·대상·비용·한도·선발 방식의 새 오판0건. 발견 즉시 수정하되 원래 오류 점수는 보존 |
| 미검증 노출 | 공개 데이터/승인 상태 변경0건 |
| 누락률 | 사람이 만든 필수 조건 정답의 누락수/전체 필수조건수. A 대비 비퇴행 확인. 2개 조건만 뽑는 제한 시험 금지 |
| 운영 | 예산/도메인/robots 위반0건. 실패와 요청 수 전부 기록 |
| 시간 | 동일 검토자가 검토에 쓴 분 단위 시간 기록. 정답 작성 시간은 따로 기록 |
| 한계 | 출처별 성공/실패/캐시/첨부 미지원·미수집 영역을 명시 |

달성조건 미달은 phase2/3 미통과다. 기준 변경은 이유·새 버전을 기록하고 다음 독립 표본부터 적용한다. API 모델의 품질·실제 usage·월 비용은 별도 phase5까지 판정하지 않는다.

## 결과 한 건의 필수 기록

case_id, cohort, category, seed_url, candidate_id, baseline_commit, snapshot_hash, checked_at, issuer_url, document_hashes, claims(값·근거·조건), unresolved, conflicts, publication_status=review_only, novelty_class, duplicate_key, deadline_status, request_attempts, cached_reads, elapsed_seconds, reviewer_minutes, reviewer_type, verdict, rejection_reason.

접속 실패도 같은 case_id로 남긴다. 원문 연락처·개인정보를 불필요하게 모델 입력이나 공개 보고서에 포함하지 않는다.

## 추가 개발 실험의 질문 v2

앞선 세 묶음7/20·6/20·7/20의 미달 결과는 보존한다. 네 번째 묶음은 아직 상세를 판독하지 않은 고정 표본2개의 문서를 대상으로, 이용 결정별20문항을 먼저 등록한 뒤 상세와 공식 첨부를 판독했다. 복합 질문의 답할 수 없는 부분을 숨기지 않기 위한 질문 단위 변경이며, 기존 결과를 소급 변경하지 않는다. 문항 내 일부가 미해결·충돌이면0, 중요오류0·완전 해결10/20 기준은 유지한다. 개발 실험의 선택 효과와 질문 버전 차이를 공개하고 일반 모델 성능이나 기존 방식 대비 효과 크기를 추정하지 않는다. [사전등록](../evaluations/phase234-2026-11-05/trial04-preregister.json)과 [결과](../evaluations/phase234-2026-11-05/trial04-results.json)를 함께 확인한다. 사람 최종 채점 전 통과로 확정하지 않는다.
