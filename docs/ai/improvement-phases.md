# 개인 정보 비서 개선 단계

작성: 2026-11-14. 상태: Phase 0 완료, Phase 1 평가 도구·오프라인 기준선 구현. 실제 모델·사용자 평가와 독립 라벨 검토는 남아 있다. 후속 Phase는 미구현이다.

## 목적과 범위

사용자가 직접 검색하고 원문을 비교하는 시간을 줄이고, 관심과 상황에 맞는 새 정보를 근거와 함께 추천한다. 카테고리는 축제·장보기·보건소·혜택에서 다른 뉴스와 정보 분야로 확장할 수 있어야 한다.

가장 피할 실패는 종료되거나 유효하지 않은 내용을 현재 이용 가능한 것처럼 보여 주는 것이다. 비용 최소화 자체를 성공으로 보지 않는다. 유용한 발견과 판단에 지출하되 현재 월 $15 원장 상한·승인 모델·무료 인프라·공식 출처 정책은 유지한다. 다른 모델·검색 공급자·비용 한도·개인정보 외부 전송은 구현안과 데이터 흐름을 먼저 구체화한다. 이 계획은 그러한 변경의 실행 승인이 아니다.

## 현재 근거

- `frontend/src/beta.ts`: 프로필과 동의한 행동 기록을 브라우저에 보관한다.
- `frontend/src/BetaPanel.vue`, `published-topics.ts`: 공개 주제 카드가 있으면 행동 점수를 쓰는 로컬 경로보다 우선한다.
- `benefit_monitor/claude_trial.py`: 입력 문서와 후보를 모델에 전달한다. 자율 검색 도구 루프는 없다. 축제·혜택 입력의 `today`는 API 전송 직전에 만든다.
- `cli.py`, `ai_daily.py`, `publish.py`, `cloud_daily.py`: 카테고리별 실행·공개 연결이 분산되어 있다.
- 출처 정의·본문 재확인·자동 공개 게이트·비용 예약·규칙 카드 대체 경로는 재사용할 기반이다.

## 진행 순서

Phase 0 → 1 → 2 → 3 → 4 → 5. Phase 1에서 평가 기준을 확정한 뒤 개인화와 추가 조사의 효과를 비교한다. Phase 4 공통화는 새 카테고리 한 개를 실제로 붙이며 범위를 결정한다. 기간은 실제 기준선 측정 후 산정한다.

| Phase | 결과물 | 기대효과 | 달성목표 |
|---|---|---|---|
| 0. 작업 기반·프롬프트 정리 | 실행 안내, 진행 기록, 프롬프트 계약 | 세션마다 맥락 재구성·충돌 감소 | 실제 요청과 지침 일치, 기존 검사 통과 |
| 1. 품질·가치 측정 | 고정 평가 사례, 단계별 지표 | 비용·형식·정보 부족 중 실제 병목 식별 | 규칙 추천과 AI 추천을 같은 기준으로 비교 |
| 2. 개인화 연결 | 공통 프로필, 카테고리별 선호, 추천 근거 | 나에게 맞는 정보 선정 | 서로 다른 선호가 추천·제외 이유에 반영 |
| 3. 필요한 추가 조사 | 제한된 조사 루프, 새 출처 후보 | 직접 재검색하는 수고 절감 | 누락 조건을 근거로 보충하고 예산 안에서 종료 |
| 4. 카테고리 확장 구조 | 등록 계약과 공통 실행 절차 | 카테고리 추가 시 수정 범위 축소 | 기존 카테고리 회귀 없이 새 카테고리 추가 |
| 5. 비용 배분·운영 개선 | 작업별 모델 평가, 재사용, 개인 브리핑 | 같은 비용으로 유용한 발견 증가 | 품질·신선도 유지하며 가치당 비용 개선 |

- [ ] 실제로 필요한 새 카테고리 한 개로 추가 절차와 변경 파일 수를 측정한다. 분야는 Phase 2 사용자 피드백으로 선정한다.

기대효과: 새 카테고리를 추가할 때 공통 파이프라인의 여러 분기를 함께 고쳐야 하는 부담을 줄인다.

달성목표: 새 카테고리 추가에 기존 카테고리 모듈 수정이 필요하지 않고, 공통 실행기는 등록만으로 이를 호출한다. 수집 실패가 다른 카테고리의 유효 결과를 없애지 않으며, 모든 공개·재배포 경로의 철회/만료 검사가 동일하게 작동한다.

검증: 기존 카테고리 계약 테스트, 공개 스냅샷 호환 테스트, 전체 Python/프런트 검사와 주요 탭 E2E. 마이크로서비스·DB·범용 플러그인 플랫폼은 요구가 생기기 전 도입하지 않는다.

## 선택과 복구

- 전면 재작성보다 기존 수집·검증 기반에 개인화와 제한된 조사를 연결하는 방식을 선택한다.
- 프롬프트 변경은 기존 스키마와 실제 게이트의 예제를 먼저 검증한다. 보류가 늘면 이전 프롬프트로 되돌린다. 원장·기존 조사 기록은 지우지 않는다.
- 각 Phase는 구현과 관측을 나눈다. 단위 테스트 통과는 사용자 유용성·실제 모델 성능·운영 배포 완료를 뜻하지 않는다.
- 구현 단위는 작게 나누되 "한 세션 하나"를 절대 규칙으로 삼지 않는다. 중단 가능한 검증 단위를 완료한 뒤 다음 작업으로 이동한다.
