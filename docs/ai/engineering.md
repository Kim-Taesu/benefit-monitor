# Agent 작업과 운영 AI 설계

## 두 실행 주체

개발 agent는 코드를 수정하고 테스트한다. 제품 내 AI는 정해진 입력으로 사실을 추출·대조하고 추천한다. 개발 도구의 effort, slash command, MCP 설정을 제품의 Claude Messages API 기능으로 간주하지 않는다.

현재 모델 호출은 `thinking={'type':'disabled'}`와 고정 모델 정책을 사용한다. 사용자가 제공한 low/medium/high/xhigh/max 분류는 작업 난이도에 따른 배분 아이디어로만 참고한다. 실제 제공자·모델·버전의 지원 값을 확인하기 전 API 옵션으로 넣지 않는다. 세션 중 모델 변경이 이전 대화나 파일을 자동 폐기한다고 가정하지 않는다.

## 개발 agent의 최소 맥락

1. 실제 cwd와 Git 디렉터리가 허용 경로 안인지 확인한다. 기본 저장소는 `.maintenance/p0-source`이며 이번 작업은 사용자 승인 워크트리 `.worktrees/phase01-evaluation`에서 한다.
2. 이 저장소의 AGENTS.md를 읽는다. 기존 예외·출처·공개 정책은 이 안내가 대체하지 않는다.
3. `git status --short`, 최근 커밋, [진행 기록](progress.md)을 확인한다. 다른 작업의 변경을 보존한다.
4. [단계별 계획](improvement-phases.md)에서 이번 작업 한 단위를 골라 관련 코드·테스트만 읽는다.
5. 입력 → 처리 → 출력과 호출자를 확인하고 목표·검증 방법을 기록한 뒤 수정한다.
6. 검사·diff 검토 후 완료/미완료/다음 작업을 기록한다. 커밋·push·배포는 별도 권한 범위다.

RTK.md, karpathy-guidelines.md, verification-discipline.md는 이 세션의 지침에서 참조되지만 상위 프로젝트와 실제 저장소에서 발견되지 않았다. 없는 지침을 읽었다고 기록하거나 내용을 추측하지 않는다.

## 작업 지시 템플릿

```text
목표: 사용자의 어떤 탐색·판단 부담을 줄이는가?
현재 근거: 관련 코드, 재현 사례, 이미 시도한 방법.
범위: 수정할 경로와 유지할 공개 계약·예산·정책.
입력: 필요한 맥락과 빠져 있는 맥락.
완료 기준: 관찰 가능한 결과와 실패/경계 사례.
검증: 실제 실행할 명령, 수동 확인, 온라인 검증 여부.
결과: 변경 파일, 실행 결과, 미검증, 다음 작업.
```

모르는 개인 선호를 추측하지 않는다. 계획의 목표치를 실측값처럼 쓰지 않는다. 한 기능의 구현→검사→기록을 마치고 다음 단위로 이동한다. 세션을 바꾸거나 압축하기 전 미완료·실패·다음 명령을 기록한다. 새 세션은 기록과 실제 diff를 다시 대조한다.

## 제품 AI의 맥락 계약

기본 kind별 입력은 유지한다. 추가 조사 모드만 공통 목적·미확인 목표·공식 링크 선택지·남은 예산을 제한된 `investigation` 맥락으로 제공한다. 아래 나머지 필드는 공통화 설계이며 모두 API에 추가된 것은 아니다.

| 영역 | 목적 |
|---|---|
| 작업 목표·기준 시각 | 무엇을 판단하는지, 어느 시점의 결과인지 |
| 후보·근거 ID·확인 시각 | 출처 역추적과 신선도 판단 |
| 명시적 선호·제외·동의 상태 | 개인화 Phase에서만 사용, 공개 데이터와 분리 |
| 이전 추천·변경 요약 | 반복 노출 감소 |
| 미확인 질문·허용 도구·남은 예산 | 조사 agent의 다음 행동과 종료 제한 |
| 출력 계약·실패 상태 | 호스트가 실행·공개 여부 판정 |

필요한 문서만 작업 시점에 읽는다. 관련 근거를 자른 경우 잘림을 기록하고, 빠진 조건을 "없음"으로 판단하지 않는다. 근거는 주장 단위로 연결하고, 본문 변경·취향 변경·프롬프트 변경을 서로 다른 재처리 원인으로 기록한다.

## 실행 장치와 완료 판정

이미 있는 JSON Schema, `review()`, 자동 공개 게이트, 월 비용 예약 원장, 입력 검증, 규칙 카드 대체, 만료·관리자 철회를 재사용한다. 이번에는 별도 agent 프레임워크·스케줄러·DB를 추가하지 않는다.

평가 계약과 실행 결과는 분리한다. 향후 결과에는 계약 버전, 입력·프롬프트·코드 해시, 명령, 종료 코드, 실제 검증 시각, 실패 이유를 남긴다. `passes: true` 하나는 검증 증거가 아니다. 테스트 통과는 모델 품질·실제 사용자 만족·배포 성공을 대신하지 못한다.

현재 Markdown 체크박스와 이 문서는 안내이며 강제 권한 장치가 아니다. 도구 권한·네트워크·비용 제한은 실제 실행 환경과 호스트 코드가 강제해야 한다. hooks 예제를 설치했다고 가정하지 않는다. 전역 설정·플러그인·비밀 파일을 변경하지 않는다.

평가 세트의 정답은 구현자가 통과시키려고 바꾸지 않는다. 기준 자체가 잘못되었으면 근거와 변경안을 기록하고 기준 변경과 구현 수정을 분리한다. 중요한 변경은 수정 권한 없는 별도 리뷰에서 반례·근거·재현을 확인한다. 모델 리뷰도 테스트를 대체하지 않는다. 병렬 작업은 독립 파일 소유권과 명시적 위임 범위가 있을 때만 한다.

## 도구 선택

아래 저장소는 2026-11-14에 참고했다. 설치나 전역 활성화는 하지 않았다. 기본 도구로 해결되지 않는 병목이 확인될 때만 도입한다.

- [RTK](https://github.com/rtk-ai/rtk): 출력 압축 후보. 원래 명령의 종료 코드와 실패 원문을 보존해야 한다. 절감률을 이 프로젝트의 실측값으로 쓰지 않는다.
- [CodeGraph](https://github.com/colbymchenry/codegraph), [GitNexus](https://github.com/abhigyanpatwari/GitNexus): 의존관계 탐색 후보. 우선 `rg`와 호출자 확인을 사용하고, 도입 시 둘 중 하나를 선택해 허용 저장소만 색인한다.
- [ponytail](https://github.com/dietrichgebert/ponytail), [grilling](https://github.com/mattpocock/skills/blob/main/skills/productivity/grilling/SKILL.md): 최소 변경과 요구 검증의 참고. 현재 작업에 필요 없는 상시 지침은 더하지 않는다.
- [Context7](https://github.com/upstash/context7): 라이브러리 문서 확인 후보. 버전 변경 작업에서 공식 문서·잠금 버전을 먼저 확인하고 필요할 때만 사용한다.

제공된 Claude Code 명령 목록은 이 환경의 검증된 명령 목록이 아니다. 설치된 도구의 도움말·공식 문서로 확인하기 전 실행 절차에 고정하지 않는다. 이번 사용자는 프로젝트 하위 worktree를 승인했지만 `/batch`의 생성 경로·위임·실행은 별도로 확인해야 한다. 외부 경로에 만드는 방식은 허용하지 않는다.

## 검증 명령

- Python 전체: `python3 -m unittest discover -s tests -v`
- 프롬프트 예시·조립: `python3 -m unittest discover -s tests -p test_prompt_examples.py -v`
- 프런트 변경 시 `frontend`에서 `npm test`, `npm run typecheck`, `npm run build`
- 사용자 동작 변경 시 `frontend`에서 `npm run test:e2e`와 해당 화면 확인

의존성 설치·온라인 호출을 검사 명령에 몰래 넣지 않는다. 기존 테스트가 네트워크나 저장소 밖 쓰기를 요구하는지 확인한다. 실패하면 테스트를 삭제하거나 성공으로 바꾸지 말고 원인·영향·미검증 상태를 기록한다.
